# Fluence

I have just built my first major project, which also stands as my longest-running project to date. After mastering HTML, CSS, and JavaScript, I built a web-based UI builder and visual editor from scratch—essentially a custom DOM manipulator engine. Because I started this without prior knowledge of pre-built frontend libraries, the core builder logic has zero dependencies on frameworks like React. However, the platform itself utilizes Node.js, Express, and Mongoose for backend cloud saving. It is a zero-dependency builder that does not rely on libraries like React or GrapesJS to function. The core builder logic is written entirely in Vanilla JS, with the UI built using HTML and Vanilla CSS.

## CORE BUILDER ARCHITECTURE

* When initialized, the builder injects an iframe (with its own isolated DOM) inside the UI, acting as a virtual browser environment for the project preview.
* After the iframe and global variables (DOM root, stylesheet references) initialize, Fluence loads an object called `project_state`. The entire project's DOM is saved inside `project_state`, which acts as a hierarchical JSON-based tree (a virtual DOM). Every element and its properties are stored with a unique key generated by the builder, alongside its relational definitions. The objective of `project_state` is to maintain a structured AST of the project that can be saved and retrieved instantly.
* The tree nature of the `project_state` object enables the builder to traverse it as a multi-way tree. Furthermore, the unique key mapped to every spawned element enables O(1) time retrieval of any element and its properties, bypassing computationally heavy tree traversals.
* `project_state` is then processed by a global rendering function. Its core objective is to traverse every element inside the state tree and inject them into the real DOM of the project (the iframe's DOM) so the project is displayed in real-time. [Virtual DOM (`project_state`) ---> Real DOM (HTML, CSS)]
* Apart from the global rendering function, the builder features a user-event-triggered element rendering function. Its objective is to read user input (the specific element the user wants to spawn), fetch the JSON-based virtual DOM snippet from a generalized recipe object, and traverse that recipe tree to render the element into the project's DOM. It then creates a unique ID for the spawned element, prepares a virtual JSON DOM object containing all specifications and structural relations, and stores it in `project_state` as a key-value pair.
* Fluence maintains an index map object mapping all project DOM elements to their respective objects in `project_state`. The state object also holds a direct reference back to the live DOM element, forming a bidirectional tracking system. This allows the user to change specifications of an element at extremely low latency.
* Fluence utilizes a central focus system. A user can select a physical element or a CSS selector targeting elements in the iframe, and the central focus system updates the focus pointer. It then dynamically populates all sub-tabs (CSS, attributes, etc.) with the values of the currently focused element.
* The engine utilizes six primary state-handling functions: three for handling attribute changes and three for styling (CSS). One reads user input from the properties tabs and applies changes directly to both the rendered iframe DOM and the `project_state`. Another syncs values from `project_state` back to the input tabs, and another handles individual element syncing.
* The input format Fluence takes from the user in the specifications tab is completely different from the syntax actually applied to the element itself (e.g., separating values and units in the UI versus combined strings in the CSSOM). To handle this, Fluence utilizes multiple string decoders to format, fetch, and display values without rendering errors. [Specifications Tab -> Input Reader -> String Decoder -> Final Applicable Value -> `project_state`] [Specifications Tab <- Final Displayable Value <- String Decoder <- Specifications Reader <- `project_state`]
* The input reader dynamically relies on the builder UI's dataset attributes to identify necessary operations and route them to the correct string decoder.
* Upon a successful specification change, a debounced autosave function is invoked to store the updated `project_state` in the database.

### Clipboard Operations
Fluence features built-in clipboard operations (Cut, Copy, Paste, Duplicate). This clipboard system entirely bypasses the native OS clipboard and the browser's `navigator.clipboard` API. Instead of copying raw HTML strings, it executes deep clones of the virtual DOM JSON state tree into a globally scoped JavaScript variable.

* **Copy():** Takes a DOM element, retrieves its unique ID via the index map, and fetches its object from `project_state`. The target object and its entire subtree are traversed to create a deep clone, which is stored in the global clipboard.
* **Paste():** Takes the deep-cloned object from the global clipboard, assigns it a newly generated unique ID, updates the hierarchical relation wires, and finally invokes the global render function on the root node to construct the live DOM version.
* **Cut():** A synchronous wrapper function that first invokes Copy() to save the deep clone, then deletes the target element (from both the live DOM and `project_state`), entirely removing it from the JSON state tree.
* **Duplicate():** Automates a rapid copy-paste cycle. It invokes Copy() on the target element and then immediately invokes Paste() using the target's parent element as the destination container. Note: All clipboard operations trigger a flush of any pre-existing data in the global clipboard variable to prevent conflicts.

### Element Deletion Mechanism
* Fluence includes an element deletion mechanism that strips the target element and its descendants from `project_state`, the live DOM, and all index map references. It operates by traversing down to the absolute leaf node of the target object, deleting all descendant nodes from bottom to top during backtracking, and finally triggering `withdraw_focus` to purge the last reference.

### Animation Controller
Fluence has a separate mechanism to handle stylesheet-based directives, including the creation and modification of animations and global CSS selectors:

* All user-declared animations are stored inside a global directives object. Every animation object maps specific timeline percentages to the CSS properties applied at that point.
* When `animation_creator()` is invoked, it prompts for an animation name, generates an object, and sends a POST request to the backend. Upon a successful save, it stores the object in the global directives, updates the UI lists, generates a boilerplate animation rule string, and injects it into the CSSOM. The CSSOM rule index is saved, and the built-in animation editor is launched.
* The builder isolates the editing process to prevent accidental mutation of the actual project layout. It creates a deep clone of the animation object as a backup in case the user aborts.
* It launches a dedicated iframe for the editor preview, hiding the main project viewport, and spawns a dummy element inside to serve as a visual preview.
* Animations are edited via classic percentage-based timelines. The editor UI functions like a video editor, allowing users to scrub the timeline slider to any percentage and generate or delete keyframes.
* Every generated keyframe creates an empty mapped object inside the animation's directive.
* When the user manipulates the dummy element's styles, the editor stores those modified values specifically inside the active keyframe's object.
* The timeline itself is maintained via a custom doubly-linked list simulated across an array of length 101 (representing 0% to 100%). Every keyframe object maintains a reference to its immediate next and previous nodes, handling additions and deletions via standard linked-list insertion algorithms.
* When the user scrubs the slider, the editor performs bidirectional traversal from that index to find the nearest linked-list node. It aggregates the styles for that specific timeframe and applies them to the dummy element for a live preview.
* Upon saving, the editor traverses the entire linked list from head to tail, converting all keyframe objects into a valid CSSOM rule string. It locates the old rule using the cached CSSOM index, deletes it, appends the new rule, and updates the index before destroying the editor instance and backup memory.

### Selector Controller
* The selector system shifts the engine from generating simple inline styles to declaring and managing global CSS rules. It enforces standard CSS cascading rules for classes, IDs, tags, and attributes.
* Users can write raw CSS selectors or use the built-in selector formatter. The builder actively calculates the real-time relative specificity of the selector while two string decoders convert inputs between strings and UI formatters. The saved selector is stored in a local `selector_order` array, sorted strictly by specificity magnitude, before being injected into the CSSOM.
* The builder tracks all elements targeted by individual selectors using a Map, binding an element's unique ID to a Set of all selector indices affecting it.
* When element or selector specifications change, the builder dynamically rebuilds this mapping object.
* Fluence utilizes "context hijacking" to edit global CSS rules. When a selector is targeted, the builder spawns a dummy element, injects it into `project_state` under the hardcoded ID `element-1`, and shifts central focus to it—tricking the builder into treating the selector as a physical DOM element.
* Users can then edit global CSS styles using the pre-existing inline-style editing architecture (listeners, decoders, and updater functions).

### Viewport Resizing & Dragging
* Fluence provides a viewport resizing mechanism so users can preview their UI across any display size. It mathematically manipulates the preview and editor iframes using CSS transforms and cross-document event listeners. When a user defines a specific height, width, and zoom, the handler applies the physical dimensions via inline styles and the zoom via `transform: scale`. Because extremely large viewports (e.g., 4K, 8K) cannot physically fit on smaller monitors (e.g., 1080p), the builder auto-calculates a scaling coefficient (max window dimensions divided by actual viewport dimensions) and applies the maximum safe scale dynamically.
* The free-drag mechanism is significantly more complex than standard drag-and-drop. Because users build responsive layouts using relative units (%, vw, vh), pixel-based dragging would destroy responsiveness. The builder spawns a selector box containing five interaction dots (left, right, top, bottom, move) over the focused element. A `sync_selector()` function continuously adapts to the element's dimensions and coordinates. When a dot is dragged, the builder records the initial coordinates, computed dimensions, and relative unit inputs. It continuously calculates mouse displacement in pixels, updating the live DOM. Upon mouse release, the builder performs a reverse-mathematical conversion to translate the final pixel dimensions back into the initial relative units. The same logic applies to translation via the move dot (calculating top/left offsets), provided the element's position is not static.

### Global Export System
* Fluence provides a global export mechanism that converts the user's project into a raw HTML file. Upon invocation, the builder fetches the raw innerHTML string from the project's DOM, iterates through the CSSOM rule array to fetch all CSS strings, and injects those rules into a `<style>` tag. This compiled HTML string is then converted into a downloadable Blob.

## BACKEND ARCHITECTURE & LIMITATIONS

The backend is the most flawed part of the project. To save the user's `project_state` in the cloud, Fluence relies on a custom Node.js and Express backend.
* **Authentication:** Due to a lack of knowledge regarding industry-standard security practices during development, the authentication mechanism is highly insecure. Upon registration/login, the backend generates a random string token, stores it in MongoDB, and sends it to the frontend in plain text. The frontend stores this token in `localStorage` (making it vulnerable to XSS). Every HTTP request includes this token, which resets on session initialization.
* Passwords are stored as plain strings in MongoDB without encryption.
* It utilizes the Mongoose ODM to store data directly, adding an extra validation layer.
* **Routing handles incoming requests:**
  * `POST /register`: Receives username, password, and email. Ensures the username is unique, creates the MongoDB document, generates the auth token, and returns it.
  * `POST /login`: Verifies user credentials in the database and returns a fresh auth token.
  * `POST /project`: The origin endpoint for all state changes. Handled by a router-level middleware that checks for a valid auth token. Includes sub-routes like `/project/save` (updates the `project_state` in MongoDB) and `/project/initialize` (creates a new project object with a unique ID).

## LIMITATIONS OF THE BUILDER

* Users cannot currently create Single Page Applications (SPAs), as the builder lacks frontend routing (like React Router).
* A major portion of the logic relies on synchronous JavaScript, which can bloat and lock the main thread.
* Lacks a JS manipulation mechanism, meaning users cannot currently script custom UI interactions.
* Code lacks modularity; excessive use of global variables severely impacts maintainability.
* No current mechanism to write custom CSS or arbitrary HTML attributes outside the visual editor UI.
* The custom clipboard bypasses the OS default clipboard, preventing cross-tab copy/pasting.
* Suffers from "reinventing the wheel"—too many native browser mechanics were rebuilt from scratch.
* No mechanism to write `@media` queries.
* No support for CSS `display: grid` interfaces.

## DEPLOYMENT

* Fluence is deployed on AWS.
* It runs on an AWS free-tier EC2 instance (Ubuntu) to ensure 24/7 uptime.
* The main script is executed via PM2 to keep the Node application alive in the background.
* Nginx is configured as a reverse proxy, redirecting HTTP (80) and HTTPS (443) requests to the application's internal port.
* Hosted on a custom domain ("fluencebuilder.in") mapped to the VPS IP.
* SSL/TLS secured via Certbot with the Nginx plugin to enforce HTTPS.
